# Capability Gap Decision Tree：能力缺口决策树

## 定位

Capability Gap Decision Tree 是 v5.5 Phase 2B Minimal Capability Runtime 的补充机制。

它解决的问题是：Master 在 Tool Discovery / Capability Matching 后发现能力缺失时，
不能只停留在“缺少工具”的汇报，而必须做出受控决策。

当 Master 发现当前环境缺少某种能力时，必须选择以下路径之一：

- `degrade`
- `substitute`
- `install_or_enable`
- `generate_temporary_capability`
- `manual_handoff`

该机制不新增 schema，不自动安装工具，不自动生成 Skill，也不设计大而全 capability registry。

## 能力缺失的定义

能力缺失指：当前 Execution Contract 所需能力，无法被当前环境中的安全、可用、
可验证工具直接满足。

能力缺失可能来自：

- 当前环境没有所需 CLI / MCP / Skill / 本地程序；
- 工具存在但权限不足；
- 工具存在但无法验证输出；
- 工具存在但风险等级过高；
- 工具版本不兼容；
- 工具能力与任务需求只部分匹配；
- 需要外部系统、凭据、网络或用户授权；
- 所需专业判断不在当前 Master 能力范围内。

如果缺失的是专业判断能力，而不是工具能力，应优先进入 Specialist Review /
Counter-Agent / Experience Review，而不是安装工具或生成脚本。

能力缺失不是失败结论，而是进入决策树的触发条件。

## 为什么不能只汇报“缺少工具”

只汇报“缺少工具”是不完整的，因为它没有回答：

- 缺失能力对任务目标有什么影响；
- 是否能降级完成；
- 是否有安全替代工具；
- 是否值得请求授权；
- 是否可以生成临时能力；
- 是否必须人工接管；
- 如果继续执行，如何验证结果；
- 如果不能执行，如何清楚地阻塞汇报。

Master 的职责不是简单报错，而是把能力缺口转化为可决策路径。

## 决策总览

```text
发现能力缺失
    ↓
评估影响：是否阻塞核心目标？
    ↓
能否安全降级？
    ├─ 是 -> degrade
    ↓
是否已有安全替代工具？
    ├─ 是 -> substitute
    ↓
是否值得请求用户授权安装 / 启用？
    ├─ 是 -> install_or_enable
    ↓
是否可以生成一次性临时能力？
    ├─ 是 -> generate_temporary_capability
    ↓
manual_handoff / blocked report
```

默认优先安全、低成本、可验证路径，但路径选择必须根据 Execution Contract、风险等级和
用户目标判断；该顺序不是强制线性流程。

路径选择必须基于 Execution Contract，而不是基于用户原始模糊需求。

## 路径 1：degrade

### 定义

`degrade` 是在不新增工具、不请求高风险授权的情况下，缩小范围或降低交付等级，
完成仍有价值的结果。

### 触发条件

适用：

- 缺失能力不是核心目标；
- 降级后仍能满足主要用户价值；
- 降级不会误导用户；
- 降级结果可验证；
- 降级不会扩大风险；
- 用户没有明确要求完整能力。

示例：

- 无法生成真实 UI 截图时，先交付结构草图和组件说明；
- 无法调用外部 API 时，先生成本地 mock 数据方案；
- 无法部署时，先完成本地构建和部署说明。

### 禁止事项

禁止：

- 隐瞒降级；
- 把降级结果说成完整结果；
- 降级到无法满足核心目标；
- 在高风险任务中用降级绕过授权；
- 用降级替代必须用户确认的决策。

### 验证要求

必须说明：

- 降级范围；
- 保留了哪些核心价值；
- 缺失了哪些能力；
- 如何验证降级结果；
- 后续恢复完整能力需要什么条件。

## 路径 2：substitute

### 定义

`substitute` 是使用当前环境中已有的安全替代工具完成同等或近似能力。

### 触发条件

适用：

- 替代工具已存在；
- 替代工具风险更低或相当；
- 替代工具输出可验证；
- 替代工具不改变 Execution Contract 的核心目标；
- 替代方案不会引入明显质量损失。

示例：

- 用 PowerShell 代替缺失的 shell 工具；
- 用 Python 标准库代替外部 JSON formatter；
- 用本地静态检查代替暂不可用的外部服务；
- 用已有 MCP 替代未安装的插件。

### 禁止事项

禁止：

- 使用未知或不可验证替代工具；
- 为了替代而扩大任务目标；
- 用不等价工具完成关键任务却不说明差异；
- 绕过安全授权；
- 使用会产生外部副作用的替代工具而不确认。

### 验证要求

必须说明：

- 替代工具是什么；
- 与原能力的差异；
- 为什么替代足够；
- 验证命令或验证信号；
- 如果替代失败，下一步 fallback。

## 路径 3：install_or_enable

### 定义

`install_or_enable` 是请求用户授权安装依赖、下载工具、启用 MCP、修改配置或授予权限。

这是高风险路径，不能自动执行。

### 触发条件

适用：

- 缺失能力是核心目标必需；
- 没有安全降级或替代路线；
- 安装 / 启用后的结果可验证；
- 用户收益明显大于风险；
- 操作范围、影响和回滚方式可以说明。

如果安装、启用或生成临时能力会污染环境、改变全局配置、引入长期依赖或难以回滚，
应优先 manual_handoff，而不是自动继续。

### 必须用户授权的操作

以下操作必须等待用户明确授权：

- 安装依赖；
- 修改配置；
- 下载外部工具；
- 启用 MCP；
- 执行未知脚本；
- 写入系统路径；
- 修改凭据、token、权限；
- 启动长期后台服务；
- 访问外部账户或敏感数据。

### 禁止事项

禁止：

- 自动安装；
- 自动启用 MCP；
- 自动修改配置；
- 自动执行安装脚本；
- 为了方便而扩大权限；
- 在未说明风险时请求用户授权；
- 授权一次后无限扩大操作范围。

### 验证要求

必须说明：

- 要安装 / 启用什么；
- 来源是什么；
- 影响哪些路径或系统；
- 风险等级；
- 是否可回滚；
- 授权后如何验证成功；
- 如果失败如何回退或停止。

## 路径 4：generate_temporary_capability

### 定义

`generate_temporary_capability` 是创建一次性、局部、可审计、可删除的临时能力，
例如临时脚本、临时检查器、临时转换器。

临时能力不是正式 Skill。

### 触发条件

适用：

- 当前环境缺少小范围自动化能力；
- 用临时脚本能显著降低人工错误；
- 输入输出明确；
- 作用范围局部；
- 可通过 diff、日志、测试或 JSON 解析验证；
- 不涉及高风险外部副作用。

如果安装、启用或生成临时能力会污染环境、改变全局配置、引入长期依赖或难以回滚，
应优先 manual_handoff，而不是自动继续。

示例：

- 生成一次性 JSON 格式检查脚本；
- 生成临时 Markdown 行宽统计脚本；
- 生成本地文件转换脚本；
- 生成临时数据校验器。

### 禁止事项

禁止：

- 生成长期后台服务；
- 生成不可审计脚本；
- 生成会自动删除、覆盖、上传或发布的脚本；
- 将一次性脚本直接沉淀为 Skill；
- 绕过用户授权执行高风险操作；
- 在缺少验证标准时生成临时能力。

### 验证要求

必须说明：

- 临时能力解决什么缺口；
- 输入和输出；
- 影响范围；
- 是否写文件；
- 如何验证；
- 使用后是否删除或保留；
- 是否值得未来沉淀为 Skill。

## 路径 5：manual_handoff

### 定义

`manual_handoff` 是当缺口无法安全降级、替代、安装启用或生成临时能力时，
向用户或人工操作者明确阻塞点和下一步选择。

### 触发条件

适用：

- 缺失能力涉及敏感权限；
- 必须用户登录、授权或提供凭据；
- 风险过高；
- 目标冲突无法自行解决；
- 关键信息缺失且无法只读获得；
- 继续执行会误导用户；
- 无法验证结果。

### 禁止事项

禁止：

- 把可自行解决的问题交给用户；
- 用笼统问题打断用户；
- 要求用户做不必要的技术判断；
- 隐瞒已经尝试过的安全路线；
- 在没有选项的情况下只说“无法完成”。

### 验证要求

必须输出：

- 阻塞原因；
- 已尝试或已排除的路线；
- 用户需要决定什么；
- 推荐选项；
- 每个选项的风险和结果；
- 等待用户确认前不继续执行的边界。

## 安全授权规则

Capability Gap Decision Tree 必须遵守 Security Capability Skill 的风险分级。

以下操作默认需要用户授权：

- 安装依赖；
- 修改配置；
- 下载外部工具；
- 启用 MCP；
- 执行未知脚本；
- 修改系统路径；
- 修改凭据、token、权限；
- push / release / deploy；
- 删除、覆盖、迁移数据；
- 上传敏感数据；
- 启动长期后台服务。

授权请求必须是具体的：

```text
我需要执行什么
为什么需要
影响范围是什么
风险等级是什么
是否可回滚
如何验证
如果不授权，替代路线是什么
```

## 与 Minimal Capability Runtime 的关系

Minimal Capability Runtime 负责：

- Tool Discovery；
- Capability Matching；
- CLI / MCP / Skill / script / manual route 选择；
- Security Capability 判断；
- Skill Deposition 判断。

Capability Gap Decision Tree 位于 Tool Discovery / Capability Matching 之后，真实执行之前。

它回答：

```text
能力缺失后，Master 应如何继续？
```

它不替代 Minimal Capability Runtime，而是补齐能力缺口后的决策分支。

## 与 Security Capability Skill 的关系

Security Capability Skill 负责风险分级。

Capability Gap Decision Tree 使用风险分级决定：

- 是否可以直接降级；
- 是否可以使用替代工具；
- 是否必须授权；
- 是否禁止自动执行；
- 是否应人工接管。

高风险路径不能因为“能力缺失”而绕过安全边界。

## 与 Skill Deposition 的关系

临时能力不等于正式 Skill。

`generate_temporary_capability` 只用于一次性、局部、可验证的缺口补足。

只有满足以下条件，才考虑沉淀成 Skill：

- 重复出现；
- 流程稳定；
- 输入输出明确；
- 验证标准明确；
- 封装后减少上下文和错误率；
- 权限边界清楚；
- 失败路径可描述。

单次任务生成的脚本、检查器或转换器，不应自动进入 Skill。

## 与用户最小打断原则的关系

Master 应优先寻找安全替代和降级方案。

不应打断用户的情况：

- 可通过只读检查解决；
- 可通过已有工具替代；
- 可安全降级；
- 可生成低风险临时能力；
- 可采用安全默认值。

只有以下情况才打断用户：

- 权限操作；
- 不可逆操作；
- 成本风险；
- 用户偏好；
- 目标冲突；
- 关键信息缺失。

用户打断必须是可决策的，而不是把所有不确定性抛给用户。

## 最终输出格式建议

本轮不新增 schema。后续如果工程化，可以使用以下结构：

```json
{
  "missingCapability": "",
  "impact": "",
  "candidateRoutes": [
    {
      "route": "degrade | substitute | install_or_enable | generate_temporary_capability | manual_handoff",
      "reason": "",
      "riskLevel": "L0-L5",
      "requiresUserAuthorization": false
    }
  ],
  "selectedRoute": "",
  "riskLevel": "L0-L5",
  "requiresUserAuthorization": false,
  "verificationPlan": "",
  "fallback": ""
}
```

## 最终原则

1. 能力缺失不是失败结论，而是决策入口。
2. Master 不能只说“缺少工具”，必须给出可执行路线。
3. 安全降级和替代优先于安装新工具。
4. 安装、启用、配置、未知脚本必须授权。
5. 临时能力不等于正式 Skill。
6. 高风险缺口必须进入人工确认或阻塞汇报。
7. 所有路径都必须有验证计划和 fallback。
