# 按需澄清方法

本文件供 [独立入口](../SKILL.md) 按需读取。它提供判断抓手，不要求完整走完每一项。目标是形成可交接的需求，不是替用户定架构或执行方案。

## 从表达回到目标

先用用户已有信息描述三件事：遇到什么问题、想发生什么变化、指定了什么交付或手段。缺少其中某项并不自动触发追问：判断它是否影响当前规划。

“想做网站”可能是交付要求，也可能只是想到的手段。可用实际使用场景说明差别，例如“客户需要在下单前预览照片排版”；若用户已说明必须使用网站且给出理由，保留网站边界。不要用模型认为更简单的方式强行替换。

遇指代、转写或名词歧义，先寻找本次材料中的可指向对象；仍有两个会改变目标的解释时，只核实那个区别。明确任务/项目归属，不能把别处已知的部署平台、设备权限或受众移过来。

## 专业补全先说明必要性，再回到本阶段

每个专业补充要能解释其与目标的关系。区分必要需求、建议、待确认推断；不能把习惯性的行业全套配置都加入一期。下面是可迁移检查例子，不是关键词分类器。

| 场景 | 只在影响当前目标时检查 | 适合的证据或可观察标准 | 常见越界 |
|---|---|---|---|
| 软件或流程 | 谁执行何种业务动作；输入与输出；聊天式或可视化交互是否影响必要能力；关键异常与数据边界；已有系统限制 | 一段真实主流程、样本数据、现有操作记录；如“用户能找到上次记录并修改指定字段”，验证方式可用人工走查 | 单人工具自动加多租户、付费、微服务；在需求澄清时锁定数据库或技术栈 |
| 内容或文档 | 面向谁、用来做什么决定；必须覆盖的论点或材料；长度、语气、交付形态；哪些结论需要原始证据 | 原始材料、受众要求、审阅主体；如“审阅人能定位每个结论的来源”，无需凭空设定数字指标 | 对文档任务追问数据库；把转述当原始数据已核验；把模型补充观点说成用户指定 |
| 设备只读诊断 | 当前允许读取什么；要识别哪种状态；已有日志、接口说明、时间与环境条件；是否需要原始记录来判断 | 提供的日志、照片的已提取信息或真实只读检查结果；如“输出异常依据与未知项，不写入参数” | 因未来可能控制而阻断当前规划；假装已连上设备；把诊断意图当写入授权 |

缺少原文时先标明当前掌握的只是摘要。若原文影响本次分析结论，提出材料请求；若仅在未来执行验证时才需要，保留执行条件并继续可以安全完成的需求整理。图片、检索、设备和文件读取是宿主可选能力，不可用就保留请求，不假定存在 OCR、RAG 或外部工具。

## 少量问题、场景、反例与样例

问题应能写清“关联哪个缺口、为什么现在需要、答案改变什么”。不为补全形式提问；用户已经无歧义给出的要求不再请求确认。

最小追问是只保留有决策价值的问题，不是固定一轮一问。已有完整信息时零追问；两个独立关键边界可以并列或合并。未暂停时，候选请求仍按契约覆盖所有当前开放缺口；暂停时保留缺口但清空请求。执行/未来缺口保留但不强行提问。先使用已有回答；若不同问法实际重复同一判断，应删去重复问题或说明新增的信息需求。不能通过删除缺口、默认用户认可或压低验收标准获得“少问”的分数。

遇抽象质量词，可以请求一个具体使用时刻、一个不希望发生的结果，或给两个短的表达性例子让用户修正。选项只是帮助比较，不暗示用户已选择推荐方向，也不将列出的选项声称为全部可能。

例如“专业一点”的文档，可以用两句语气不同的文字对照；“更方便”的流程，可以对照两个简短操作路径。用户认可哪个元素，就记录哪个元素，不把认可扩大为整套实现和外部操作许可。涉及真正制作应用、复杂界面或外部系统的验证请求交给下游，澄清阶段只描述需要验证的判断。

没有新增信息时改变切入角度；如果仍没有进展，保留未知或暂停。不要用另一种说法无限重复同一问题，也不以已问几轮作为就绪证据。

## 离线修复与输出边界

区分模型候选的格式/来源修复与向用户澄清：同一可信输入、同一 previous 下，首次
候选之后最多 2 次额外修复，可预登记更低值，首次不计入修复数。每次都重新运行确定性校验，
不能相信模型或 trace 自填的 valid。只修复有证据支持的问题，不改写用户来源；
若需要新材料或用户决定，应在有效候选中保留具体缺口及请求，交宿主检查后处理；无效时不得抢先追问。改 state ID、换错误类别或清空错误记录
都不重置这条链。上限内成功即可停止；上限后才正确也算超限，不能选择性丢掉前面失败。

到限仍无效时输出检查失败，保留未决事项、错误与上一有效结果；没有上一有效结果
就说明没有。检查器不会替模型修复、重试或生成规范 paused 状态。只有宿主依据真实
暂停/资源来源提供 control，且候选本身通过契约，才有可交接的 paused 结果。
补充真实用户输入后可以建立新一轮，但所有轮次/失败/输出消耗都需纳入活动记录。

每次候选最多 65,536 个原始 UTF-8 字节。宿主在开始前登记只能下调的工程上限，
成对评测使用相同值，模型不得自行增加；更低的现有资源额度优先。超限即停止，
保留文件引用和摘要，不能截掉尾部、删历史来源/硬约束或偷偷再试。这个检查器不实现
活动级调用预算或运输控制；它只检查传入的同一轮候选序列，不认证记录是否完整。

输出应简洁且完整：只给候选 JSON，由工具产生摘要，不复制整套方法或讲评过程。
优先删重复叙述，保留来源关联、稳定 ID、冲突双方、未知和修订记录。计数必须先读
原始字节，不先 strip、统一换行或解析再序列化：中文、emoji、CRLF、空白、JSON
转义及失败输出都会影响实际长度。另报 canonicalStateUtf8Bytes 和
renderedSummaryUtf8Bytes 仅用于比较规范状态和逻辑摘要；它们不是原始输出或落盘
summary.md 的大小（平台换行可能不同）。这些数值不等于 Token，也不证明费用上界。

questionCount 仅统计 method=user 的请求条数，requestCount 统计全部方法的请求条数；
一条请求可能包含多个问题，因此实际问句数和用户负担由评审另记，不能用条数冒充。

[离线检查器](../evals/interaction_checks.py) 可拒绝相同 method、gapRefs、问题及样例
的重复（忽略空白和 request ID），并复用契约拒绝追问已关闭/未来/执行缺口。不同
问法覆盖同一缺口只产生待审标记；换 gap ID 的语义重复、暗中漏掉需求、答案是否已知
仍需独立评审。待审标记使宿主进入人工复核，不自动展示问题或追加修复。只有有效状态的 computed nextStep 为 ready_for_planning 才零追问交接；取证、样例与暂停分别处理。结构检查通过不能证明问题数已最少，也不能证明短输出更好。

## 成功标准与局部修订

标准要描述用户能观察的结果，并给出适用验证方式和证据类型/确认主体。可以是人工走查、用户评价某一明确维度、原始材料核对或后续真实设备验证。不编造数值目标，不把工具/环境尚不可用当作需求不明。

同一标准未变时保留稳定 ID。收到新条件后区分：

- **需求变化**：用户改变目标、范围或结果要求。记录变化来源，保留旧版本与失效事项，重评受影响标准。
- **理解修正**：原理解与已有来源不符。记录纠正依据，修正受影响事项，不伪称用户刚刚改变主意。
- **执行问题**：结果未达现有标准。保留标准与缺口，交执行/校验层处理；不能为了宣布完成自动降低标准。

交付端改变不代表业务目标全部推倒重来。保留无关硬约束和授权范围；依赖被替换或失效标准的请求、待办或交接应标记需重评。标准 ID 仍有效不等于旧结论自动有效，也要检查内容和依赖是否受改动影响。

## 证据评审边界

本地工具能检查结构、重复 ID、引用、原话匹配、修订关系和规则一致性；无法证明专业补充必要、用户语义被忠实理解或引文确实授权某动作。审阅时回到原始输入，看是否偷换目标、扩范围、虚构确认、静默丢冲突、降低标准。没有真实模型行为评测时，保持 `BEHAVIOR_NOT_VERIFIED`。
